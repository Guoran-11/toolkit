## 5. 已知缺口与契约差异

**依赖真实网络 / 外部引擎 / 磁盘，只能手工验收：**

- 短链真实跳转（TC-02/04/05 展开环节）：自动化只覆盖提取与逐跳白名单/SSRF 校验，
  真实 DNS/重定向需现场验；不触网是本仓库测试的硬约束。
- 断网重试（TC-14）、磁盘不足 507（TC-19）、仅音频真实转码（TC-11）、产物 TTL 与 404（TC-16）：
  自动化只覆盖判定逻辑（重试参数、限流、归一化、去重/过期判定），端到端结果需真实环境。
- 抖音/快手真实作品解析：依赖分享页 `_ROUTER_DATA` / `__APOLLO_STATE__` 与平台签名/风控，
  本机无有效样本且反复试探会触发风控，未做真实请求；失败时按契约返回 `PARSE_FAILED` /
  `RISK_CONTROL` 并降级到 yt-dlp（可选）。
- 真实平台下载未执行：本机网络带宽受限（依赖下载约 10 KB/s），17 MB 级样本会占用数十分钟；
  下载链路已用本地 Range 服务器做字节级校验（1 MiB 完全一致）。

**实现与契约文字描述的差异（按实际代码写测试，未改后端）：**

1. **B站 HTML 降级**：契约 §4.1 的降级链写的是「公开接口 → 分享页 HTML → yt-dlp」，
   实际 `adapters/bilibili.py` 只有 JSON 接口（view + playurl），未实现分享页 HTML 解析，
   因此夹具 `bilibili/page_initial_state.html` 仅作样本保留、未被解析用例引用。
2. **快手需登录/会员作品**：实际抛 `VideoParseError`（`PARSE_FAILED`），未细化为
   `LOGIN_REQUIRED` / `VIP_REQUIRED`；测试断言为允许集合。
3. **抖音 `item_list: []`（失效作品）**：实际抛 `VideoParseError` 而非 `ITEM_NOT_FOUND`
   （页面没有 deleted 标记时无法区分）；真实 404 页面仍映射 `ITEM_NOT_FOUND`。
4. **`normalize_quality` 只看高度**：竖屏作品（1080×1920）会被归一为 `2K`；
   夹具因此采用横屏尺寸，避免把该实现特性误判成解析错误。
5. **媒体直链过期（403）**：目前重试一次后返回 `DOWNLOAD_FAILED`，未实现「自动重新解析再下」
   （契约 §9.3 建议项），列为 P2。
6. **Cookie 加密**：本机未安装 `cryptography`，走模块内 HMAC-SHA256 计数器流 + HMAC 校验的
   降级实现（文件权限 0600）；安装 `cryptography` 后自动使用 AES-GCM（代码优先分支）。
7. **限流为进程内计数**：多 worker/多进程部署时阈值会被放大，需要外部存储才能全局生效（P2）。

## 7. 2026-10-21 缺陷修复：视频下载链接不能被正确解析

### 7.1 现象与生产证据

用户报障「视频下载链接不能正确被解析」。生产审计日志（`storage/logs/audit.log`）显示：

```
2026-10-20T23:20:35  video.download  bilibili  480P  result=submitted
2026-10-20T23:20:35  video.download  bilibili  480P  result=failed  error_code=DOWNLOAD_FAILED
2026-10-20T23:20:40  video.download  bilibili  480P  result=submitted
2026-10-20T23:20:40  video.download  bilibili  480P  result=failed  error_code=DOWNLOAD_FAILED
```

`storage/logs/toolkit.log` 对应失败文案：`该清晰度没有可用的媒体地址，请重新解析后再试`。
即：解析看起来成功、用户也能看到清晰度下拉，但选中「默认清晰度」后拿不到媒体地址。

### 7.2 根因（生产真实链接复现）

在服务器上用真实 B站链接复现：

| 链接 | 前端默认选中 | 结果 |
|------|--------------|------|
| `BV1xrnz6gEVD`（现代稿件） | `format_id="64"`（720P，无地址占位项） | `LOGIN_REQUIRED`（误报登录） |
| `BV1xx411c7mD`（老稿件） | `format_id="32"`（480P，无地址占位项） | `DOWNLOAD_FAILED`（与生产日志一致） |

根因链（`app/modules/video/adapters/bilibili.py::_build_formats`）：

1. DASH 流的 `format_id` 用「高度反查 qn」生成；老视频 DASH 高度是 384（不在 `_QN_HEIGHT` 表），
   反查失败后退回 `entry["id"]`（=32），与 `support_formats` 补出的 480P 占位项 `format_id="32"`
   **撞车**。
2. B站 DASH 同一 qn 会返回 3 个编码（codecid 7=AVC / 12=HEVC / 13=AV1），`format_id` 全部相同。
3. 无媒体地址的占位项被标记 `need_login=False`（720P 等），前端「可用清晰度」过滤与后端默认选择
   都把它当成可用。
4. `VideoItem.format_by_id()` 取第一个匹配项；formats 按高度倒序，占位项排在真实流前面
   → `downloader.select_format()` 拿到 `url=None` 的项。
5. 前端读取 `item.default_format_id`，但 `VideoItem.to_api()` 从未输出该字段。

### 7.3 修复内容

| 文件 | 改动 |
|------|------|
| `app/modules/video/adapters/bilibili.py` | qn 优先取 `entry["id"]`；同 qn 多编码只留 AVC（同级取最大码率）；`format_id` 改 `dash-{qn}-{codecid}` / `durl-{qn}` / 占位项 `{qn}`；无地址占位项未登录时 `need_login=True`；`covered_qns`+`covered_heights` 防重复 |
| `app/modules/video/models.py` | `VideoFormat.to_api()` 新增 `available=bool(url)`；`format_by_id()` 多命中时优先有地址且非会员项 |
| `app/modules/video/adapters/base.py` | `pick_default_format()` 跳过显式无地址候选（无 `url` 键视为可用性未知） |
| `app/modules/video/downloader.py` | `select_format()` 命中无地址项先回退同 quality 可播放项；按 VIP → 登录 → 无地址 报错，删除「任意项需登录就报登录」的误报逻辑 |
| `app/modules/video/service.py` | `_parse_one()` 输出 `default_format_id`（成功与 `LOGIN_REQUIRED` 路径共用） |
| `app/static/js/views/video.js` | 新增 `isFormatUsable()`；默认清晰度优先 `default_format_id` 并排除 `available=false`；下拉置灰不可用项；无可用清晰度时给占位 option；批量栏过滤 |
| `app/modules/video/adapters/douyin.py`、`app/modules/video/net.py` | 抖音分享页改版后需匿名访客 Cookie：新增 `http_post_json()`（保留逐跳 SSRF 校验）与 ttwid 进程内缓存/重试链路（6h，Cookie 不入日志） |

契约扩展（向后兼容）：`formats[].available`、`item.default_format_id`，详见
`docs/视频下载模块-实现契约.md` §3.2 / §4.1 / §5.1 / §5.2。
